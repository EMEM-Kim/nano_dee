# 웹 대시보드 학습 정리

## 1일차 — 질문을 그래프로 바꾸기

질문은 “호흡기 질환 청구가 겨울에 더 많은가?”로 정했다. 독자는 병원 경영기획 담당자, 활용 시점은 월초 회의다. 시간 순서를 비교하므로 꺾은선 그래프를 사용하고 축·단위·출처·집계 기준을 함께 표시했다.

`main_sick`가 J로 시작하는 명세서를 `recu_fr_dd`의 월로 묶었다. 2024~2025년 24개월 중 11~3월 10개월과 6~9월 8개월은 기간 길이가 다르므로 총합 대신 월평균으로 비교했다. 각각 742.1건과 341.875건으로 약 2.17배다. 이 관찰만으로 계절이 질환을 유발했다고 말할 수 없다.

## 2일차 — 지표·조인·상호작용

| 지표 | 정의 | 주의점 |
|---|---|---|
| 명세서 수 | 필터 후 행 수 | 방문·환자 수와 다름 |
| 총 진료비 | rvd_rpe_tamt_amt 합계 | 단위 원 |
| 수진자 수 | 고유 jid 개수 | 월별 수진자 수를 더하지 않음 |
| 건당 진료비 | 총 진료비 / 명세서 수 | 기관별 환자 구성·입원 비중을 조정하지 않음 |

`claim.yid = institution.yid`, `claim.main_sick = sick_master.sickcd`를 연결했다. 기관명은 `code_table.code_type = '종별코드'` 조건을 함께 적용해야 다른 코드 유형과 섞이지 않는다. 원본의 명세서·기관 키 중복과 기관 조인 누락을 검사했다.

전체 KPI·차트·표가 같은 필터 상태를 사용하게 했다. 상병과 기관 간 비교에는 가로 막대, 월별 변화에는 꺾은선을 사용했다. 표와 CSV를 제공해 시각화에서 본 값을 확인할 수 있도록 했다.

## 3일차 — 배포·연결·반복 작업

기본 제출물은 정적 스냅샷이다. CSS·데이터·스크립트를 포함한 한 HTML 파일이라 파일을 내려받아 열 수 있고, GitHub Pages에서도 실행된다. 데이터가 갱신되면 원본 추출과 빌드를 다시 해야 한다.

선택 확장으로 Supabase CSV 테이블과 읽기 전용 RLS, 페이지 단위 조회, 오류 메시지를 준비했다. 연결형에서는 새로고침 때 데이터베이스를 다시 읽는다. WebSocket 실시간 구독은 구현하지 않았다. 실제 프로젝트 URL과 공개 키가 없어 라이브 연결 완료로 표시하지 않는다.

AI에 전달할 때는 독자·질문·열 이름·조인 키·계산식·단위·제출 파일 형식·검산 기준을 구체적으로 작성한다. 재현 프롬프트는 `submission.md`, 반복 검증은 `scripts/test_web.mjs`, 배포는 워크플로로 정리했다.

## 배운 점

화면이 그려지는 것과 숫자가 맞는 것은 별도 문제다. 원자료 집계, 필터 결과, 코드값 매핑을 확인한 뒤 해석을 붙여야 한다. 파일이 저장소에 올라간 것과 다른 사람이 공개 URL로 접속할 수 있는 것도 별개이므로 배포 성공을 따로 확인한다.
