# 웹 대시보드 강의 회고 — 검토 후 제출용 초안

공개 URL(배포 확인 후 제출): https://EMEM-Kim.github.io/nano_dee/dashboard.html

이번 강의에서 정리한 핵심은 대시보드를 만들기 전에 “누가, 얼마나 자주, 무엇을 결정하기 위해 보는가”를 정해야 한다는 점이다. 숫자와 차트를 많이 넣는 것보다 독자가 답을 얻을 수 있는 지표를 선택하는 것이 중요하다. 이를 바탕으로 병원 경영기획 담당자가 월초에 청구 규모와 진료 수요를 점검하는 상황을 설정했다.

kr_claims 수업용 가상 데이터를 이용해 명세서 수, 총 진료비, 고유 수진자 수를 KPI로 구성했다. 상병별·기관 종별 비교에는 막대그래프를, 시간에 따른 변화에는 꺾은선 그래프를 사용했다. 수진자 수는 명세서 수와 다르고, 월별 고유 수진자를 단순 합산하면 중복 계산된다는 점을 지표 정의에 반영했다. 또한 기관 종별 진료비 차이는 상병 구성과 입원 비중을 고려하지 않은 값이므로 진료의 질이나 효율로 단정하지 않도록 설명했다.

이번 결과물은 ChatGPT Codex의 도움으로 구현했으며, 강의의 원본 데이터에서 계산한 값을 독립 집계 결과와 비교했다. 전체 38,375건, 총 진료비 3,293,580,300원, 고유 수진자 2,970명을 확인했다. AI에 요청할 때도 화면 디자인뿐 아니라 계산식, 단위, 조인 키, 중복 제거 기준과 검산값을 구체적으로 전달해야 한다는 점을 배웠다.

백엔드와 데이터베이스 개발 분야에 적용한다면 API 요청량, 오류율, 응답시간의 변화와 서비스 이용 흐름을 한 화면에서 점검하는 운영 대시보드로 확장할 수 있다. 예를 들어 웹 서비스에서는 요청 수, 완료 비율, 응답 지연을 연결해 사용자가 어느 단계에서 이탈하는지 확인할 수 있다. 이때 KPI의 분모와 기간을 명확히 하고 개인정보는 집계된 형태로 다루는 설계가 필요하다.

3일차 자료에서는 CSV를 다시 배포하는 정적 방식과 Supabase 테이블을 읽는 동적 방식의 차이를 정리했다. 기본 제출 파일은 정적 스냅샷이다. 실제 Supabase 연동은 수행하지 않았으며, 데이터베이스 연결은 향후 확장 과제로 남겼다. 다음 단계는 공개 읽기 범위를 제한한 데이터베이스를 연결하고, 값 변경 후 화면의 집계가 갱신되는지 검증하는 것이다. 반복되는 검산과 배포 절차는 재현 가능한 프롬프트로 정리해 유지보수에 활용하고 싶다.
